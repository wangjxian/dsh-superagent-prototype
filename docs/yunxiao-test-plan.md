# 固定 QA 集成分支交付实测计划

当前流程：全部涉及工程本地单测 → 将工作项分支通过 MR 或直接合并到工程固定 QA 分支 → 处理冲突 → 触发各工程普通 QA 流水线 → 所有部署和共享 QA 环境测试通过 → 完成工作项并写汇总评论。工作项分支仍只用编号，不加前缀。

## 1. 范围与配置

- 仅两个云效沙箱仓库 test-agent（7643728）、test-agent-service（7644238），项目 yedou-test（ef26d3d0f9c77de54a9a1c5105）。本轮完整验证后，将原型累计改动提交到 feat/yunxiao-integration；不推送原型分支。
- 两项目各自的 QA 流水线为 5362874、5363213，代码源固定 release/qa 分支，不开启 Flow branchMode。旧 qa 及其他分支和历史发布记录保留。
- 当前自动接单仅 Bug；Task 规则保持停用，不扩大正式业务接单范围。
- 准备工具的完整 projects 清单含 repository、pipeline_id、unit_test_command、merge_mode（direct 或 merge-request），QA 分支由流水线源读取并固定。

## 2. 安全与问题处理

1. 只写上述沙箱仓库、沙箱项目和两条沙箱 QA 流水线；不碰真实项目、生产流水线、数据库或凭据。
2. 不删除任何既有分支，不 force-push，不 reset 别人的历史。固定 QA 通过保留双方历史的合并推进；冲突只在本轮 <编号>-qa 分支解决，开发分支保持纯净。
3. 合并前核对开发分支受测提交、QA 当前头和最新流水线运行。存在进行中的构建时等待；状态读取失败就报告，不猜测。完成前核对实际构建的 QA 提交及部署版本。
4. 写操作结果不明确时，先读取实际运行与远端状态进行核对，不盲目重试。
5. 旧 MR !1、!2 及旧分支保留；旧合并确认不再触发合并。
6. 云效网页操作使用已登录 Chrome；命令行使用现有 aliyun 账号。需要新的密钥时由用户安全配置，不读、不打印或记录秘密值。
7. 意外写入立即暂停并正常停止测试服务（暂停接口只阻止后续调度，不能取消已有 worker），报告证据，等用户回复再修正。按计划故意制造的沙箱集成冲突属于预期测试。

### 2.1 发现问题时怎么处理

- **核心流程阻塞立即修**：参数/字段错误、接单或完成状态错误、分支丢失、流水线集成或 QA 主流程失败、写回失败。修代码、补行为用例，跑 `LC_ALL=C pnpm check`，记录进行中的工单和运行，重启服务，回归出问题的步骤。
- **小问题累计修**：不影响主流程的文案、提示、日志、展示等，记入结果文件待修，继续测；阶段结束后批量修复、检查、重启，只回归受影响步骤。
- 同一个写操作修了两次还是失败，就停下来，报告现象、日志与判断。
- 所有检查使用 `LC_ALL=C pnpm check`；重启后核对工单、运行与确认记录未丢失。

## 3. 固定分支集成协议

1. 确认项目清单，提交干净的工作项开发分支，通过 orchestrator_qa_prepare 真正执行全部本地单元测试。
2. 推送受测提交，通过 orchestrator_qa_integrate 合入 release/qa。直接合并保留原 QA 头和受测提交；MR 以受测开发分支或已受测的 <编号>-qa 为源，并保留源分支。切换 QA 专用 MR 后，关闭并停止跟踪原开发 MR，保留其历史。
3. 合并冲突时不启动流水线；从受测开发提交创建 <编号>-qa，在独立 QA worktree 合入最新 QA、保留双方内容解决。开发分支保持不变。全部工程重测，prepare 中添加 integration_branch 后重试；QA 专用分支不得合入 master/release。
4. 合并确认后才触发该固定 QA 分支的普通流水线。核对实际 run.sources 中的分支和提交，不能拿旧分支管理器输入代替实际构建版本。
5. 各工程 QA 发布成功后，在共享常驻 QA 环境运行 orchestrator_qa_test。允许通过 deployments 指定同事后续发布的实际运行；QA 当前头和实际构建必须包含本工单受测开发/QA候选提交。部署标识匹配实际 qaCommit/pipeline/run 后测业务 HTTP，不要求等于首次发布的 QA 头。
6. 完成评论给出简短单测/验收结果、QA 短提交、MR 和流水线链接及环境；完整输出保留在内部工单。非修复结论不伪装成已修复，也不走修复 QA 门禁。
7. prepare/integrate 在任何写入前拒绝配置了 source triggerEvents 的流水线。手动 QA 管理与代码自动触发不可混用，宿主不自动修改用户触发策略。
8. 重开复用既有 worktree 和分支，保留未提交内容。pre-push 拒绝非快进、删除和旧改投分支；真正的主干保护由 Codeup 服务端配置。测试超时可设置 timeout_ms，涉及工程之外不做远端分支扫描。
9. QA/开发分支被远端重建时，本地跟踪缓存必须更新成功，再由包含关系或受测提交检查给出明确结果；Codeup 不得为评审署名改写历史。仓库评论使用名称，内部继续用 ID 校验。
10. 流水线 YAML 的固定 QA 目标变更时，空闲交付可直接重新 prepare 采用新分支，不手工清 KV；运行中构建或开放 MR 必须先完成/取消/关闭。旧验收缓存失效，历史报告保留。
11. release/* 服务端保护可能覆盖 release/qa；按项目确认 agent 的该分支推送权限或采用 merge-request 并满足审批。本轮不修改服务端权限。已退役 MR 索引应清理，真正待评审记录保留到可确认结束。

## 4. 本轮实际验证

- SIQB-5 从两个仓库各自的 master 开发，只新增独立验收程序；前端通过 MR、后端通过直接合并进入 release/qa。
- 两个仓库各预置 QA-only marker，与开发新增的同名文件冲突；两模式都必须先发生一次真实冲突。验证冲突期间不启动新流水线；旧开发 MR 由 QA-only MR 替换并关闭。
- 只在 QA 专用分支解决冲突、重新全部单测、合并和发布。独立验证开发分支与原提交完全一致，且不包含 QA 独有历史。共享 QA 后续前移的包含判断由本地回归覆盖，本轮不为此多启动一次流水线。
- 各项目重复 integrate 返回同一运行，最终各只增加一次流水线。在独立常驻 QA 环境验证真实前后端调用、双 marker 及部署版本，自动完成后检查简短评论使用仓库名称。保留旧分支，只推进 release/qa 和本轮编号/QA-only 分支。
- 历史 Flow branchMode 实测仅为旧流程记录，不能当作新流程验证。具体运行、提交、冲突和未覆盖项写入 [实测结果](yunxiao-test-results.md)。
