---
name: dsh-superagent-codeup
description: Deliver to Aliyun Yunxiao Codeup: workspace repositories, bugfix and feat branches, merge requests with their work items, and the target release.
---

Deliver through Yunxiao Codeup with `aliyun devops`, as the account `$DSH_SUPERAGENT_YUNXIAO_ACCOUNT` of the organization `$DSH_SUPERAGENT_YUNXIAO_ORG`: every subcommand takes `--organization-id $DSH_SUPERAGENT_YUNXIAO_ORG`. The host gives the CLI its yunxiao token for the call, so never read, print or pass a token yourself, and never act as another account.

The workspace is `$DSH_SUPERAGENT_WORKSPACE`: every repository in it whose remote is on codeup.aliyun.com may be delivered. Give each repository the ticket involves a worktree of its own under `$DSH_SUPERAGENT_DIR/<repository name>`, branched from `origin/master` (`origin/main` where there is no `master`, or the branch the assignment names), as in `git -C $DSH_SUPERAGENT_WORKSPACE/<repository name> fetch origin` then `git -C $DSH_SUPERAGENT_WORKSPACE/<repository name> worktree add -b <branch> $DSH_SUPERAGENT_DIR/<repository name> origin/master`. Work in those worktrees and never in the checkouts of the workspace itself, which stay as the operator left them; a ticket that changes several repositories gets one worktree and one merge request per repository. `orchestrator_codeup_target` takes a repository id, by `group/name` or by the directory name, when the assignment involves more than one.

Name the branch `bugfix/<yymmdd>-<description>-<number>` for a defect and `feat/<yymmdd>-<description>-<number>` for a task: `<yymmdd>` is the day the work starts in Asia/Shanghai, `<description>` a few lowercase words, and `<number>` the work item's serial `$DSH_SUPERAGENT_YUNXIAO_SERIAL` such as AXOAXO-6812 when the ticket names one, otherwise the ticket's short name `$DSH_SUPERAGENT_NAME`. The host binds the merge request when the branch's last path segment ends with that serial or with `$DSH_SUPERAGENT_NAME` after a dash, so keep it last; a retarget branch adds `-to-release-<yyyymmdd>` after the name of the branch it moves. Each commit message names the work item the ticket names and links it, as in `fix: keep the session alive (AXOAXO-6812)` followed by the work item's address, and commits as the author the Delivery requirements section names, otherwise as `$DSH_SUPERAGENT_YUNXIAO_ACCOUNT`.

Push only `bugfix/` and `feat/` branches: the worker's pre-push hook refuses every other branch and every branch deletion, and the host refuses a merge request whose source branch is neither. A `release/` branch belongs to the host.

Before opening a merge request, call `orchestrator_codeup_target` with the repository and read the `target` it answers: the release branch that merge request must target. Never work that date out yourself — the host knows which release merged back into master, and creates the day's release from master when it must. Then open the merge request with `aliyun devops codeup-create-change-request --organization-id $DSH_SUPERAGENT_YUNXIAO_ORG --repository-id <id> --source-project-id <id> --target-project-id <id> --source-branch <branch> --target-branch <target> --title <title> --work-item-ids <work item id>`, where `<id>` is the numeric repository id `orchestrator_codeup_target` reports, and report it at once with `orchestrator_report` and `changes: [{ repository, localId }]`, which binds its thread to this ticket.

Write the result on the merge request with `aliyun devops codeup-create-change-request-comment --organization-id $DSH_SUPERAGENT_YUNXIAO_ORG --repository-id <id> --local-id <n> --comment-type GLOBAL_COMMENT --draft false --resolved false --patchset-biz-id <patch set> --content <text>`, where `<patch set>` is the `patchSetBizId` of the latest `MERGE_SOURCE` entry of `codeup-list-change-request-patch-sets`: a status line first, then the root cause, the change and the verification evidence, briefly. The host appends the marker that keeps the comment from starting a new ticket and the line that says an agent posted it, so do not add either. Never paste the body of a SQL statement, a credential or private Feishu content into a merge request; name the statement and where it lives instead.

Merging, approving, closing and changing a work item are a person's work on Codeup, and the host performs them: merging only after the approver confirmed the target release in Feishu, and changing the work item when the ticket ends. A worker delivers the branch and its merge request; never claim a merge, an approval or a result that did not happen. Once the merge request is self-reviewed and its checks pass, call `orchestrator_request_merge` with it; the approver's answer comes back to this ticket. Until the merge and the PRE verification are done, report progress, never ready: a ready report ends the ticket.

After the merge the host tells this ticket so. Then deploy and verify on PRE yourself: find the pipeline by name — a `qa-` one for the QA environment and a `pre-` one for PRE, such as `pre-axo-manager-x64` — with `aliyun devops flow-list-pipelines --organization-id $DSH_SUPERAGENT_YUNXIAO_ORG`, start it with `flow-create-pipeline-run --pipeline-id <id>`, and follow the run with `flow-list-pipeline-runs --pipeline-id <id>` and `flow-get-pipeline-run --pipeline-id <id> --pipeline-run-id <run>` until it ends. A failed task's log is `flow-get-pipeline-job-run-log --pipeline-id <id> --pipeline-run-id <run> --job-id <job>`: a defect in the change is yours to fix, an occasional failure is `flow-retry-pipeline-job-run` with the same three ids, and a run that needs a person is a blocker to report. `qa-` and `pre-` pipelines are the only ones you may start or retry; the forwarding script refuses every other name, and one the ticket needs anyway is `orchestrator_request_pipeline` — the host asks the approver on Feishu and starts it for you when they agree. `prod-` and `prod-pre-` pipelines are never a worker's.

A ticket that needs a statement handled it as a SQL action: the file, its title, the target database, whether it runs before or after the deployment, the statement, the statement that undoes it, and a read-only query answering 1 or 0 that shows whether it took effect. The files go into the merge request, in the directory the repository already keeps its migrations in, and the result comment names the files only — never a statement's body. QA statements you run yourself, and record what they returned. Statements for PRE wait for the approver: call `orchestrator_sql_approval` with every statement the ticket needs, in one call, and the host sends them the full SQL, the target database and the check query; their answer comes back to this ticket, and only then do you run the approved statements. A PROD statement is never a worker's, whatever the ticket says.

Run an approved statement with the credentials you read from 1Password for that environment, never with one written into a file or a log. Before running it, check that the file's content is the one the approval names — the note carries the fingerprint — and run a statement once per target: a second run of the same statement needs a new approval. When the result is unclear, such as a timeout after the statement was sent, do not retry: check with the query, report what you found, and let a person decide.

Once PRE is deployed, reproduce the original problem there and verify the fix, then report ready with the `verification` field naming what you ran and what it showed. A verification that fails, or a person writing on the work item, the Feishu conversation or the merge request, brings the ticket back to you.
